# 需求文档

## 1. 问题定位（取证结论）

用户要连接 Galatea 的 MCP 服务（`https://galatea.abysllumina.com/mcp`），在「手机能力 → 远程 MCP 导入」里点"安全检查"连续两轮失败。本轮取证确认了真正的根因，和前两轮的猜测都不同：

- **Galatea 官方只支持两类接入环境**：Claude/GPT/Gemini 网页连接器（OAuth）和 Claude Code/Codex/本地 IDE（token）。它**没有授权第三方自建网页应用直连**——我们的应用不在它的白名单里。
- **浏览器跨域硬限制**：即使服务端允许，MCP 握手必须携带 `Authorization`、`MCP-Protocol-Version`、`Mcp-Session-Id` 等自定义请求头，这类请求浏览器会先做 CORS 预检；只要对方没明确放行本站域名，前端 fetch 根本发不出去。沙箱侧连该域名 DNS 都无法解析，无法进一步实测，但上述协议约束已足以判定纯前端直连不可行。
- 结论：继续在"握手细节"上修补（补协议头、加日志）不会成功，必须换接入形态。

## 2. 目标与方案

让 Galatea（以及任何同类"只给标准 MCP 地址、不开放跨域"的服务）能真正接入并使用其工具。采用双通道：

### 通道 A：手动登记工具清单（必做，兜底可用）
- 远程 MCP 面板新增「手动添加服务」入口：填写服务名 + MCP 端点地址 + 访问令牌（选填），然后**逐个登记工具**（工具名、用途描述、风险等级低/中/高）。
- 提供一份常见天气/资讯类工具的快捷模板可一键填入，减少手敲量。
- 登记后的服务与自动发现的在服务列表中等价：角色聊天时可调用，调用时按既有分级确认机制执行。
- 实际调用走标准 JSON-RPC POST（带 Bearer 令牌）；若浏览器仍拦截（跨域），给出明确的人话提示："该服务不允许本网页直接调用，请在支持的客户端中使用"，不再笼统报"读取配置失败"。

### 通道 B：复制为 curl 调试指令（辅助排障）
- 对每个已登记/已发现的服务，提供「复制调用指令」按钮，生成一条包含真实端点与令牌的 curl 命令（令牌仅复制到剪贴板，不落界面明文、不写日志），方便用户在电脑终端验证服务本身是否通、区分"服务不通"还是"浏览器拦了"。

### 附带修正
- "安全检查"失败原因文案全部改成人话（DNS 解析失败 / 跨域被拦 / 需要登录 / 服务拒绝），并在面板红字直接显示，不用再去翻控制台。
- 保留现有 mcp.json 仓库导入与 OAuth 自动发现逻辑不动（对其他开放跨域的服务仍然有效）。

## 3. 涉及文件定位
- `src/lib/remote-mcp.ts`：inspectSource 错误文案细化；新增手动服务的数据结构与存储（沿用 `vp-phone:` key 前缀规范）；rpcCallTool 对手动服务复用。
- `src/components/RemoteMcpPanel.tsx`：新增「手动添加服务」表单、工具登记列表、复制调用指令按钮。
- `AGENTS.md`：静默记录本轮根因与方案。

## 4. 验收标准
1. 面板可手动新建一个服务并登记至少一个工具，保存后服务列表可见、可启用。
2. 聊天中角色触发该工具时出现对应确认级别（低/中/高行为与既有分级一致）。
3. 调用被浏览器跨域拦截时，红字明确说"该服务不允许本网页直接调用（跨域限制）"，而不是"读取配置失败"。
4. 「复制调用指令」能得到一条可直接在终端跑的 curl 命令。
5. 原有 GitHub 仓库导入与标准端点直连功能回归正常。

## 5. 本期不实现
- 不做服务端代理转发（本平台无自建后端服务，Edge Function 转发第三方任意 URL 存在 SSRF 风险且需长期维护，暂不引入）。
- 不承诺 Galatea 一定能调通——若它坚持只允许白名单客户端，手动登记后调用仍会被拒，届时以明确报错呈现。

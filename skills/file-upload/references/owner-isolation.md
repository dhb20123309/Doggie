# 本人和父对象隔离

需要“用户只能看到和操作自己的附件”时，使用 `ownership:'user'`。核心默认生成 `users/<uid>/...` 路径并在访问前检查当前身份；这只是客户端边界和路径组织，真实权限必须由 Storage RLS、角色 grants 和业务 API 强制。

公开文件 URL 可以转发，不等于附件记录或父对象可被其他用户查询。private Bucket 只控制对象访问；签名接口仍必须依赖当前用户会话和真实 policy。

如果附件关联客户、工单、巡检或团队对象，业务保存接口必须同时校验：

- 当前用户对附件 owner/路径的权限；
- 当前用户对父对象、tenant 或团队角色的权限；
- 业务记录中的 `bucket`、`objectPath` 与允许范围一致；
- UPDATE 的旧行条件和新行 owner/父对象条件都成立。

不要只相信前端过滤、`created_by`、用户提交的父对象 ID 或可伪造的路径前缀。不要把团队共享、主管例外或跨租户访问偷偷加入本人模式；这些需要单独的业务授权设计。

最小验证使用两个真实会话：A、B 都可完成自己的上传；private 模式下 B 和匿名会话不能直接读取或为 A 的已知路径签发新 URL，B 对 A 对象的覆盖、改名和删除均被拒绝；public 模式的对象读取按公开策略允许，但记录查询、业务关联和对象变更仍需隔离。业务关联失败只保留稳定引用并重试关联，不移动或删除对象。
